## Tradeoffs
- 2026-09-10T14:12:00Z — Selected Amazon SQS (standard) + SNS-fanout-from-EventBridge for C2/C8 over a bare EventBridge target: EventBridge already fans out workflow events (per unit-request-workflow infrastructure-services), but the notification worker needs at-least-once WITH a visibility-timeout lease, competing-consumers, and a native DLQ — properties SQS provides directly and the reliability-design/scalability-design require. Chose EventBridge rule → SQS queue (with redrive to an SQS DLQ) so the durable at-least-once buffer, lease, and dead-letter of ADR-NOTIF-02 are first-class rather than reconstructed on the bus.
- 2026-09-10T14:12:00Z — Kept the worker as an embedded-module consumer inside the shared Fargate monolith for the MVP (topology parity), but specified a clean split point to a dedicated queue-driven worker service/Lambda when queue-depth scaling demands it, because scalability-design mandates independent producer/consumer scaling keyed on queue depth. Documented both as one parameterised topology so environments differ only in scale.
- 2026-09-10T14:12:00Z — Chose DynamoDB for both the in-app inbox (C6) and the delivery-record store (C7): the access patterns are per-recipient keyed reads and O(1) (recipientId, dedupeKey) idempotency lookups, exactly DynamoDB's strength, and it reuses the platform's existing DynamoDB + KMS + PITR posture. Used DynamoDB TTL to enforce bounded retention (distinct from the workflow store, which explicitly does NOT use TTL).
- 2026-09-10T14:12:00Z — Chose Amazon SES for the EmailSenderPort binding (managed, pooled, native bounce/complaint feedback) over a third-party provider, aligning with the AWS-native posture and letting bounces feed the skipped(NO_EMAIL_CONTACT) / dead-letter signals.
